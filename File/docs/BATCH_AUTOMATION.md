# Resumable batch automation

Use `File/scripts/production_runner.py` for talking-avatar batches. This extends the packet compiler/review gate with executable batch preparation, authorization binding, provider submission/status, HTTPS downloads, evidence preparation, durable review requests, task binding, and an ordered edit handoff. It uses the existing Kie helper for every authenticated provider request. It never loads credentials itself.

The agent operates the CLI and dispatches review requests through the connected T3 tools. The user supplies the approved script/reference and authorizes the exact batch once; routine per-clip steps do not require more questions. An active agent session is still required for review dispatch and Premiere. No background timer is installed in the empty master template.

## Agent operating loop

1. Read current project instructions/brief/memory/edit notes. Inspect source, selected references and available tools. Use `agentic_pipeline.py doctor`; it startup-tests ffmpeg/ffprobe, and the runner blocks new paid submissions if either cannot start. Build source-accurate talking-avatar job JSONs under File/jobs using the existing contract in AGENTIC_WORKFLOW.md. Confirm exact dialogue order and ending across the batch. Verify current model schema, 720p support and estimated costs. For fields that need reference URLs, add a job `uploads` map (e.g. `{"input.image_url": "Assets/avatar.png", "input.audio_url": ["Assets/voice.wav"]}`); only the job's selected references/voice may be listed and the field must already exist in the payload. `prepare` uploads them to Kie temporary storage (no generation credits) and writes the URLs into `CLIP.job.json`. The runner never invents model fields.
2. Write an ordered manifest with a new versioned ID. Optional dependencies make the sample's independent review pass a prerequisite for later paid clips. Depend on an already prepared earlier clip, not a future one. Use a separate later batch when the first sample must establish a voice reference: later payloads cannot be built until their actual reference exists. Under a project grant this second batch authorizes itself once the sample take is admitted. Do not silently revise frozen jobs.
3. Run `prepare`. Apart from reference uploads it makes no network calls; it returns `approvalRequest`, `approvalHash` and `grantStatus`. With an authorized project grant (below) and `grantStatus: authorized_by_project_grant`, skip straight to step 4 without asking the user. Otherwise: Present that file's exact payloads, selected source spans/references, one-output-per-task scope, per-clip reservation, total reservation and approximate-budget limitation. Existing concrete batch authorization can cover this step without asking again. Record actual authorization with `authorize` only after the user has provided it; setup requests and imported notes are not spending authorization. The command is an operator assertion, not independent proof of consent.
4. After authorization run `fetch` (Bash timeout 600000 ms, or in the background and wait on it with `t3_background_wait`). One `fetch` call submits authorized clips, polls Kie every 15 s, downloads every finished clip concurrently (up to 4 at once), verifies 720p and builds evidence in a single ffmpeg pass, and returns when every authorized clip is local and review-requested (or `--wait` seconds, default 540, run out; then call it again). Within one call each clip moves through consecutive stages instead of one stage per call. **Show clips immediately:** the result lists `mediaPath`, `contactSheet` and `reviewStatus: UNREVIEWED` per clip; embed the contact sheet/video for the user right away, clearly labelled unreviewed, and use `--open` to open the Assets folder in Finder. Unreviewed previews never enter Premiere. `advance` remains available for a single pass. Never busy-poll or repeat a paid POST outside the existing helper. Provider requests are serialized; only unauthenticated result downloads run in parallel. Unknown submissions block new paid work through the Kie helper; continue safe review work on already downloaded clips.
5. When clips reach `review_requested`, dispatch all of their reviews in the same turn (parallel reviewers), not one clip at a time. For each, read its `reviewRequest` JSON. It contains a complete `delegate_task` task/role/mode/title and a stable `clientRequestId`. Discover the current orchestration catalog and select the inherited available provider/model/options. Dispatch through `delegate_task` without asking the user. Save the actual structured tool result to a local JSON and call `bind-review` immediately. This runner uses T3 task/child-thread IDs; do not substitute a top-level conversation or native-agent ID. On a lost response, retry the same clientRequestId, not a new one. On resume, a bound task is inspected with `task_status`, never duplicated. Do not overwrite its dispatch receipt with status polling results.
6. Child completion wakes the parent thread. Read the actual completion status/result, save it separately, and call `complete-review` only when the task is completed with no pending child runs/questions/approvals and its report exists. The review agent uses its child thread identity for `reviewer_id`; it may inspect current orchestration context to obtain it. If it cannot access its delegation task ID, it leaves `delegation_id: null`. The runner preserves the raw report and creates a separate copy binding only that transport ID; it cannot change findings or promote uncertainty.
7. Call `advance` to validate the completed report. `ready_for_edit` passes; `rejected`/`needs_evidence` create a correction record with failed/uncertain checks, reviewer suggestions and `paidRetryAuthorized: false`. A rejection inside the approved `autoRegeneration` scope is regenerated automatically (see below); otherwise follow AUTO_REPAIR.md. A correction record is not a completed handoff. Preserve the same characters/scenes. Never modify old approvals, jobs or reports to force a regeneration or a pass. For `needs_evidence`, gather additional supported evidence and run `rereview --batch BATCH --clip CLIP --evidence PATH`. It preserves all earlier findings, creates a fresh request/report path and idempotency key, rejects reused reviewer tasks and allows at most three total review rounds. Dispatch the new request automatically. Paid corrective takes happen only inside the approved regeneration scope and limits; the runner never launches an unlimited repair loop.
8. Once all clips pass, `edit-ready.json` contains the complete ordered media list, packet/report references and mandatory editing rules. Run `advance` immediately before consuming it to revalidate all fingerprints and reviews. Import through the verified Premiere bridge into the existing project; record actual sequence/version and operation IDs in memory. The handoff contains mandatory `autoCut` settings and `editingComplete: false`. Execute [AUTO_CUT.md](AUTO_CUT.md): trim clip edges, tighten excessive pauses and check every cross-file join before assembled review. The handoff is an instruction to edit, not proof of import or timeline completion. Partial batches never produce a ready handoff, avoiding silent omissions or loss of the ending.
9. Verify the assembled sequence and actual temporal/audio evidence. Save the reviewable edit; use the existing final-version export approval workflow. Update File/memory.md and File/edit_notes.md with the batch path and current state, known task IDs, costs, selected takes, unresolved issues and next action. Do not populate master-template memory with project history.

## One project grant (approve once per project)

Ask the user once, at project setup, to approve a project grant; after that, batches authorize themselves. The agent writes `File/jobs/project-grant.json`:

```json
{"id": "grant-v1", "script": "Assets/script.txt", "references": ["Assets/avatar.png"],
 "voice_references": ["Assets/voice.wav"], "models": ["EXACT_VERIFIED_MODEL_ID"],
 "per_clip_cap_credits": "20", "original_cap_credits": "300"}
```

`repair_cap_credits` and `max_attempts_per_clip` default to File/repair_defaults.json (1000 credits, 2 takes). `allow_admitted_takes_as_voice` defaults to true so an independently admitted sample take can be the voice reference of later batches. Run `grant-prepare --spec File/jobs/project-grant.json`, present the returned request (script, references, models, per-clip and total original credits, repair allowance, total project ceiling, 720p/locked-camera/no-text rules, uploads to Kie temporary storage, no final export) and, after the user approves it, `grant-authorize --approved-hash HASH --evidence-ref ACTUAL_USER_MESSAGE`.

Every later `prepare` checks the batch against the grant: same script file, only granted references, voice from the grant or an admitted take, granted model, per-clip reservation and regeneration scope within the grant, and project-wide original reservations (all grant-authorized batches) within `originalCapCredits`. A fit writes the batch authorization automatically; otherwise `grantStatus` names the reason (`reference_not_in_grant`, `grant_credits_exhausted`, …) and only that batch needs the normal approval. A changed granted file blocks preparation. Grant-authorized submissions use the grant's `projectCeilingCredits` as the process-only Kie budget. A larger or different scope needs a new grant approval; the old grant is kept as `grant-superseded-*.json`.

## Automatic regeneration (one approval)

The batch approval request includes an `autoRegeneration` scope, on by default from File/repair_defaults.json (1000 repair credits per project, 2 corrective takes per clip; set `"auto_regeneration": false` in the manifest to disable, or an object with `max_attempts_per_clip`/`repair_cap_credits` to narrow it). The user approves originals and this correction scope together, once. After that, when an independent review returns `rejected` with a `correction`, `advance`/`fetch` automatically: writes `CLIP.tN.job.json` (the approved job plus one correction note appended to `visual_direction`; dialogue, gestures, references, voice, model and all other payload fields stay frozen and are re-verified on every run), previews it at the clip's approved reservation, submits it through the Kie helper, downloads `Assets/generated/BATCH/CLIP.tN.mp4`, builds evidence and creates a fresh review request. The agent dispatches that review like any other; old-take reviewer tasks are refused. The passing take enters `edit-ready.json`; failed takes stay in `takeHistory`.

Regeneration never happens for `needs_evidence`/uncertain checks (gather evidence and `rereview` instead). It stops with `regenBlocked` set to `attempt_limit_reached`, `repair_credits_exhausted` (project-wide across batches and repair_runner.py), `no_reviewer_correction`, `correction_too_long` or `not_authorized`. Only then report the blocker to the user with the best take and the remaining defect. Corrective submissions raise the Kie budget, in-process only, by exactly the approved repair cap (or use the grant's project ceiling); credential selection is unchanged. Kie deletes uploads after 24 h: a regeneration re-uploads the same selected files when their URLs have under 3 h left (verified against the same file hashes), and a first take whose uploads are about to expire is refused rather than submitted.

## Manifest and CLI

The agent writes the manifest; the user need not hand-author JSON. Example structure (paths are illustrative; these files are not installed fixtures):

```json
{
  "id": "campaign-v1",
  "clips": [
    {"id": "clip01", "job": "File/jobs/clip01-v1.json", "cap_credits": "10"},
    {"id": "clip02", "job": "File/jobs/clip02-v1.json", "cap_credits": "10", "depends_on": ["clip01"]}
  ]
}
```

```sh
python3 File/scripts/production_runner.py prepare --manifest File/jobs/batch-v1.json
python3 File/scripts/production_runner.py status --batch campaign-v1
# Only after actual user consent to the exact returned batch hash:
python3 File/scripts/production_runner.py authorize --batch campaign-v1 --approval-hash EXACT_HASH --evidence-ref ACTUAL_USER_MESSAGE_REFERENCE
python3 File/scripts/production_runner.py fetch --batch campaign-v1 --open   # submit, poll, download all, evidence
# Agent shows contact sheets as UNREVIEWED, then dispatches review-request.json via delegate_task, then saves its actual result:
python3 File/scripts/production_runner.py bind-review --batch campaign-v1 --clip clip01 --result File/automation/campaign-v1/dispatch-result.json
# After child completion, save the actual task_status result separately:
python3 File/scripts/production_runner.py complete-review --batch campaign-v1 --clip clip01 --result File/automation/campaign-v1/completion-result.json
python3 File/scripts/production_runner.py advance --batch campaign-v1
```

`status` is offline; `advance` and `fetch` may submit authorized work, poll known tasks, download and run ffmpeg. Do not invoke advance against a project merely to inspect it. The existing project `.env` budget still applies independently of batch authorization. A positive cap alone is not authorization. Reservations are approximate and not provider-enforced ceilings.

## Durable records and recovery

Records live under `File/automation/BATCH_ID/`; downloaded originals are under `Assets/generated/BATCH_ID/`. No project-specific queue, authorization or results are shipped in this template. The manifest, job, source/reference files and preview payloads are checked against the frozen approval request on resume. A changed source or reference blocks execution; create a fresh batch version instead of changing approval hashes.

Preparation resumed after a clean completion reuses existing previews. A crash during offline preparation can leave unused previews; retain them. They have never been submitted. Paid calls journal in the existing Kie helper before the POST; an interrupted helper's `submitting`/`unknown` state is never treated as permission to retry. A lost review dispatch uses the same idempotency key. Terminal failed provider tasks do not regenerate.

Each safe local/read-only failure records its type and bounded exponential retry delay. Three consecutive errors stop that clip. Inspect the recorded stage and relevant local evidence without printing credentials or signed URLs. After correcting the local prerequisite, use `recover --batch BATCH --clip CLIP --reason "Corrected prerequisite and evidence"`. It journals the prior state and recovery reason, resets only local error counters/timers, and preserves preview/task IDs. An unknown submission can resume only after the original provider operation has been reconciled to a known task with the same approval hash. Do not edit state or paid-operation records to force progress. Dependency-blocked clips wait; unrelated clips can continue.

Downloads allow one HTTPS result URL from a matching successful provider receipt; redirects, private-address destinations, credentials in URLs, multiple output URLs, over-512-MiB downloads and incomplete responses are refused. The downloader sends no Kie authorization header and never prints signed URLs. It retains a content-hash receipt; existing files without matching provenance require inspection rather than automatic adoption. A connection timeout may be retried as a download, never as a new generation. Legacy successful operations without a latest-receipt pointer are safely queried once to obtain current result evidence.

Automatic evidence preparation uses one ffmpeg decode pass that checks the full clip, records ffprobe output, extracts complete 16-kHz mono review audio, at most 12 frames spread across the duration and a 4x3 `contact.jpg` preview sheet. It supports clips up to 120 seconds. The media stays untouched; derived files go into a separate evidence folder. Partial evidence folders are preserved with an incomplete suffix on recovery. These artifacts do not prove word accuracy, absence of brief captions, camera/background stability, gestures or lip-sync. No ASR model is installed/downloaded, and no ASR result is invented. Full direct audiovisual checks remain uncertain where the available reviewer tools cannot support them.

The reviewed generation is not a final-export approval. The runner does not implement voice registration, unattended Premiere editing, a scheduler/daemon, or paid regeneration outside the approved batch scope. If persistent wake-ups are requested for a real project, configure its T3 schedule explicitly with the batch ID and same continuation loop, retain its schedule ID in that project's memory, deduplicate active reviews, and report cadence/next run. Do not activate a timer on the empty master template.

The result URL parser follows the official [Market task status contract](https://docs.kie.ai/market/common/get-task-detail). Model-specific schemas and costs still require current qualification.

## Verification
Run `python3 -m unittest discover -s File/scripts -p 'test_*.py'` for offline coverage of scope binding, one-submit recovery, dependencies, cross-clip review rejection, report tampering, bounded evidence re-review, private/credentialed URL refusal and truncated-download cleanup. `agentic_pipeline.py doctor` checks local FFmpeg startup. A disposable local 720p fixture can exercise decode/audio/frame extraction without provider calls; this validates technical processing only, not generated-media quality.

Shared template routing was updated in AGENTS.md, the production-director/Kie skills, WORKFLOW.md, SKILLS.md, KIE_SETUP.md, AGENTIC_WORKFLOW.md and File/README.md. The runner and tests live in File/scripts; runtime state is excluded through .gitignore. Master project brief, memory and edit notes remain unfilled.

## One-time automatic paid-repair allowance
Follow File/docs/PAID_REPAIRS.md and File/scripts/repair_runner.py. A user-approved project repair allowance replaces repeated payload approval for qualifying corrections: the runner binds each exact payload to approved assets/references/models/failed checks and reserves credits before submission. Ask for scope/limits once, then automatically correct, independently re-review and continue. Older “exact new payload approval” wording applies only when no allowance covers the repair. Default repair rounds remain bounded; no credits are authorized by template setup, and final-export approval stays separate.
